# Deploying to a production-like VPS (k3s) with the same chart

The chart is identical to the local one. Everything that differs is in `charts/platform/values-prod.yaml`
(plus a Secret created out-of-band).

## What changes, and where

| Concern          | Local (`values-local.yaml`)                         | VPS (`values-prod.yaml`)                                                               |
| ---------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Domains          | `store.localtest.me`, `dash.localtest.me` + `:8080` | `domain.store`, `domain.dashboard` (real DNS A records → VPS IP), no port              |
| Scheme / cookies | `http`                                              | `https` (the gateway cookie becomes `Secure`, WordPress URL becomes https)             |
| Ingress          | Traefik (k3s built in), no TLS                      | Traefik + `ingress.tls.enabled` + cert-manager issuer                                  |
| Images           | built locally, imported into k3d                    | pushed to a registry: `global.imageRegistry`, pinned tags, optional `imagePullSecrets` |
| Storage          | k3s default `local-path`                            | `global.storageClass: local-path` (or your CSI class), bigger sizes                    |
| Secrets          | generated by the chart on first install             | `secrets.existingSecret` created with `scripts/create-secret.sh`, not in git           |
| Resources        | small                                               | larger requests/limits                                                                 |
| Store domains    | `<slug>.stores.localtest.me`                        | `provisioner.storeDomainSuffix` + a wildcard DNS record `*.stores.example.com`         |
| Gateway replicas | 1 (SQLite)                                          | optionally `postgres.enabled=true` and `gateway.replicas=2`                            |
| Store settings   | USD, UTC                                            | `store.currency`, `store.country`, `store.timezone`                                    |

## Steps

1. **VPS with k3s** (Traefik and `local-path` storage included):
   ```bash
   curl -sfL https://get.k3s.io | sh -
   sudo cat /etc/rancher/k3s/k3s.yaml     # copy to your machine, replace 127.0.0.1 with the VPS IP
   ```
   Open ports 80/443 (and 6443 for kubectl, ideally restricted to your IP).
2. **DNS**: A records for `shop.example.com`, `mcp.example.com` and the wildcard `*.stores.example.com` (used by stores created from the dashboard) pointing at the VPS public IP.
3. **cert-manager** (optional but recommended):
   ```bash
   helm repo add jetstack https://charts.jetstack.io
   helm install cert-manager jetstack/cert-manager -n cert-manager --create-namespace --set crds.enabled=true
   kubectl apply -f - <<'YAML'
   apiVersion: cert-manager.io/v1
   kind: ClusterIssuer
   metadata: { name: letsencrypt-prod }
   spec:
     acme:
       server: https://acme-v02.api.letsencrypt.org/directory
       email: you@example.com
       privateKeySecretRef: { name: letsencrypt-prod }
       solvers: [{ http01: { ingress: { class: traefik } } }]
   YAML
   ```
4. **Images**: `REGISTRY=ghcr.io/YOUR_ORG TAG=1.0.0 ./scripts/push-images.sh`, then set `global.imageRegistry` and tags in `values-prod.yaml` (and `imagePullSecrets` if the registry is private).
5. **Secret** (random values generated locally, never written to disk):
   ```bash
   LLM_API_KEY=sk-... NAMESPACE=platform ./scripts/create-secret.sh
   ```
6. **Install**:
   ```bash
   # edit domains / registry / admin email in values-prod.yaml first
   helm upgrade --install shop charts/platform -n platform -f charts/platform/values-prod.yaml --wait --timeout 15m
   SECRET=woo-platform-secrets ./scripts/creds.sh     # admin logins
   ```
7. **Verify**: `GATEWAY_URL=https://mcp.example.com STORE_URL=https://shop.example.com HOST_PORT= RELEASE=shop node tests/cluster-demo.mjs` (needs kubectl access to the cluster, and `LLM_PROVIDER=mock` unless a model key was set).

> **Status:** this guide was written and its values file linted and rendered (`make lint-chart`), but it was **not deployed** to a VPS during development. Expect to adjust DNS, registry and TLS details.

NetworkPolicies are enforced by k3s out of the box; check with
`kubectl -n platform run t --rm -it --image=busybox --restart=Never -- wget -qO- -T3 http://shop-woo-mcp:3000/healthz` (blocked) versus the same command from a gateway pod (allowed).

## Upgrades and rollback

```bash
# upgrade: build/push new images with a new TAG, bump the tag(s) in values-prod.yaml (or --set), then
helm upgrade shop charts/platform -n platform -f charts/platform/values-prod.yaml --wait --timeout 15m
helm history shop -n platform
# something wrong? roll back the whole release (config + image tags) to a previous revision
helm rollback shop <REVISION> -n platform --wait
```

- **Each component is independent**: change only `gateway.image.tag`, `wooMcp.image.tag`, `dashboard.image.tag` or
  `store.image.tag` to upgrade just that one; Helm only restarts what changed (the gateway also restarts when its ConfigMap changes, via a checksum annotation).
- **Data is safe across upgrades and rollbacks**: the WordPress, MariaDB and gateway volumes are separate
  PVCs (the standalone ones carry `helm.sh/resource-policy: keep`), and the Secret is kept and reused (generated values are looked up, not regenerated).
- **Stateful apps and downgrades**: WordPress/WooCommerce and the gateway may migrate their data on a newer version. Rolling back
  the _image_ of a newer database schema can be unsafe, so before upgrading the store take a backup:
  ```bash
  kubectl -n platform exec sts/shop-mariadb -- sh -c 'mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" --single-transaction wordpress' > wordpress-$(date +%F).sql
  kubectl -n platform cp $(kubectl -n platform get pod -l app.kubernetes.io/name=gateway -o name | cut -d/ -f2):/data/gateway.db ./gateway-$(date +%F).db
  ```
- With SQLite the gateway uses `Recreate` and one replica, so a rollout has a few seconds of downtime. With `postgres.enabled=true` it rolls with `maxUnavailable: 0`, a `preStop` drain delay and a PodDisruptionBudget, so users see no errors. WordPress also uses `Recreate` because its content volume is ReadWriteOnce.
- **Existing databases are migrated additively** at gateway start (new columns and tables are added). Taking a backup first is still the safe path.
- **Stores created from the dashboard** are separate Helm releases (`store` in each `store-<id>` namespace). Upgrading the platform chart does not upgrade them; set the new image tags and recreate them, or run `helm upgrade store charts/platform -n store-<id> --reuse-values --set store.image.tag=...` yourself.
- A `helm upgrade` that was interrupted can leave the release as `pending-upgrade`; delete that revision's `sh.helm.release.v1.<release>.v<N>` Secret and run it again.
- `helm rollback` also reverts a bad _values_ change (e.g. a wrong domain), not only image tags.
